# Stage Browser Control Before Linux Injection

**Build one normalized pointer stream, prove it inside an owned browser page, then connect that unchanged stream to Linux.** The shared value should begin as movement only—`(seq, x_norm, y_norm, t_ms, valid)`—after calibration, geometry, quality gates, and filtering; browser CSS pixels and Linux desktop coordinates belong only in their respective output sinks. The browser proof should use a loopback-only Server-Sent Events endpoint and a visible page-local dot, because this measures mapping, latency, stale-data behavior, and accidental activation without taking over the workstation. When that passes, the current Ubuntu Xorg development session can use XTEST for a supervised real-pointer proof; maintained Wayland support should use the user-authorized XDG RemoteDesktop portal with libei/EIS, not privileged `uinput`. **The repository is not yet ready to produce a real tracked pointer:** it currently ends at two timestamped 30 fps camera frames, while landmark extraction, calibration stages C1–C9, triangulation, ray/screen intersection, and cursor filtering remain planned ([README](../README.md), [architecture](../docs/ARCHITECTURE.md)). Start both cursor sinks with a deterministic synthetic sweep, then connect the real fusion output only after it exists. Defer clicking, multi-monitor spanning, browser extensions, WebSockets, and a backend framework until safe movement is demonstrated.

## The repository needs one stable output seam

The implemented runtime presently produces a `Frame` containing a BGR image and monotonic exposure/arrival timing; `FrameClock` de-jitters timestamps and identifies sequence gaps, but neither component produces landmarks or screen coordinates ([capture implementation](../src/eyehand/capture.py), [timebase implementation](../src/eyehand/timebase.py)). Both configured cameras run at 30 fps, so a newly observed fused cursor position will initially arrive at no more than roughly one sample every 33 ms; a display-rate renderer can repeat the newest sample, but smooth 60 Hz motion would require measured interpolation or prediction rather than faster rendering alone ([camera configuration](../config/cameras.toml), [setup measurements](../docs/SETUP.md)). The existing calibration design already supplies the correct trust boundary: bad stereo geometry should be rejected, C7 should invalidate stale geometry, and C9 should measure accuracy, jitter, and latency ([calibration plan](../docs/CALIBRATION.md)). A sink must receive `valid=false` when those checks fail; clamping a bad estimate to the screen edge would turn tracking failure into unwanted motion.

**The smallest shared contract is normalized active-panel position plus freshness and validity.** `x_norm` and `y_norm` should derive from the calibrated screen-space result after C8 correction and filtering, not from either camera image. A sequence number rejects duplicate or reordered transport samples; a monotonic timestamp enables stale-input shutdown. Activation is intentionally absent from the first contract because the project has no implemented gesture signal and an inaccurate click can cause damage that inaccurate movement cannot. Once movement is safe, an explicit intent transition can be added without changing coordinate mapping.

The likely first implementation footprint is deliberately small. A new `src/eyehand/cursor.py` can own the immutable sample, finite/range validation, and screen-to-normalized mapping; `tests/test_cursor.py` can cover bounds, invalid values, and stale samples. A new `src/eyehand/browser_cursor.py` can contain the loopback HTTP/SSE proof and its minimal page, while `src/eyehand/cli/main.py` registers one `browser-cursor` command beside the current commands. The eventual fusion loop calls the sample constructor only after its existing planned gates. The Linux stage should add one platform module only when the browser exit criteria pass; it should not alter capture, timing, calibration, or geometry. The repository-level `RTK.md` found under `.claude` governs token-efficient developer shell usage, **not application runtime or cursor architecture**, so it requires no product code or dependency.

## The browser proof isolates accuracy from privilege

Serve the demo page and `/events` from one `127.0.0.1` origin using Python 3.12's standard-library `ThreadingHTTPServer`. SSE is a native one-way browser stream with automatic reconnection, matching tracker-to-page flow without adding a package; WebSocket adds bidirectionality that this stage does not need, and WebRTC would add negotiation and signaling for a same-machine link ([WHATWG SSE](https://html.spec.whatwg.org/dev/server-sent-events.html), [Python `http.server`](https://docs.python.org/3.12/library/http.server.html), [MDN WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)). Keep a single latest sample rather than a reliable queue, because replaying old positions creates cursor lag. Bind only to loopback, expose only expected paths and methods, omit permissive CORS, and describe this standard-library server as a local diagnostic rather than production infrastructure.

The page should validate and store the newest sample in its SSE callback, then render once per `requestAnimationFrame`. It maps normalized coordinates to viewport CSS pixels, clamps only already-valid values, and moves a fixed `pointer-events: none` overlay with a CSS transform; `requestAnimationFrame` aligns the update with repaint, while `elementFromPoint` can inspect what lies below the non-targeting overlay ([MDN `requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame), [MDN `elementFromPoint`](https://developer.mozilla.org/en-US/docs/Web/API/Document/elementFromPoint)). Hiding the tab, losing the connection, or exceeding the measured freshness timeout must hide the dot, clear any synthetic hover state, and disarm activation. Calibration, smoothing, and prediction stay upstream so browser and Linux behavior do not diverge.

This synthetic cursor is intentionally not a mouse. Browser-created pointer events are untrusted, same-origin policy blocks arbitrary third-party page manipulation, and APIs such as fullscreen, file pickers, or clipboard operations can require trusted user activation ([W3C Pointer Events](https://www.w3.org/TR/pointerevents3/), [MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy), [MDN user activation](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/User_activation)). If activation is tested later, restrict it to the owned test page: visibly identify a native button or link, focus it, and call `click()` once on a validated intent edge. Do not build an extension, automation driver, Pointer Lock integration, arbitrary-event synthesizer, or browser-side tracking pipeline; none proves global Linux pointer control.

## Xorg proves movement while Wayland defines production

The observed development host is Ubuntu GNOME on Xorg, making **XTEST the smallest immediate real-cursor proof**. XTEST can synthesize core motion and button events, while upstream `xdotool` explicitly warns that its X11 approach does not work correctly under Wayland ([X.Org XTEST](https://www.x.org/docs/Xext/xtest.pdf), [xdotool](https://github.com/jordansissel/xdotool)). Use one persistent connection rather than spawning a CLI process per frame. Label the backend Xorg-only and fail closed under Wayland; attempting XTEST through XWayland would not provide compositor-wide control of native Wayland applications.

For Wayland, the supported cross-desktop path is **XDG RemoteDesktop portal authorization followed by libei/EIS input**. The portal performs `CreateSession`, pointer-only `SelectDevices`, and consent-bearing `Start`, then `ConnectToEIS` hands the session to libei; the compositor remains responsible for accepting and routing emulated input ([XDG RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html), [libei overview](https://libinput.pages.freedesktop.org/libei/)). The official `liboeffis` helper can perform that portal setup and return an EIS file descriptor ([libei libraries](https://libinput.pages.freedesktop.org/libei/libraries/index.html)). If dependency minimization matters during feasibility work, the portal's older D-Bus pointer notification methods can prove the permission flow first, but EIS is the documented maintained transport. No official first-party Python libei binding was identified, so the implementation decision is between a small native helper and the D-Bus proof—not an invented general backend system.

Do not make `uinput` the normal path. It writes a kernel virtual device through `/dev/uinput`, and tools such as `ydotool` commonly need a privileged persistent daemon; that bypasses desktop consent and expands the damage possible from a tracker fault ([Linux `uinput`](https://docs.kernel.org/input/uinput.html), [ydotool](https://github.com/ReimuNotMoe/ydotool)). On Wayland, map normalized input into the logical regions advertised by EIS rather than guessing physical pixels: those regions include compositor-owned offsets and logical dimensions and can differ from physical resolution under scaling ([libei region API](https://libinput.pages.freedesktop.org/libei/api/structei__region.html)). Version one should calibrate to one selected monitor. Full-desktop spanning, mixed scaling, rotation, hotplug, and stored permission restoration should wait for supervised compositor-specific testing.

## Safety gates determine when each stage advances

The safe rollout is synthetic logging, browser movement, browser failure handling, nested or disposable desktop injection, real Xorg movement, Wayland portal movement, and only then deliberate activation. The control state should progress from `disarmed` to `armed-move-only` and eventually `armed-click`. Tracking loss, stale input, C7 failure, portal/session closure, exception, signal, or a physical kill shortcut returns immediately to `disarmed`; any future held button must be released before emulation stops. libei explicitly requires starting emulation before sending events and releasing active state when stopping, while the Global Shortcuts portal can provide a focus-independent emergency shortcut on Wayland ([libei sender API](https://libinput.pages.freedesktop.org/libei/api/group__libei-sender.html), [XDG Global Shortcuts](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html)). During supervised early work, keep a physical mouse attached and retain terminal `Ctrl-C`; neither is sufficient for an unattended product.

| Gate | Minimum acceptance evidence | Advance when |
|---|---|---|
| Shared sample | Pure tests reject NaN/infinity, preserve valid normalized edges, reject stale/non-increasing samples, and never convert invalid tracking into edge motion | The deterministic sweep reaches all corners with correct axes |
| Browser | Latest sample wins; disconnect, hidden tab, and stale input hide/disarm; the overlay never blocks hit-testing; a supported control activates at most once per intent edge | An extended supervised run records no stale or repeated actions |
| Performance | Browser records SSE receipt with `performance.now()` and the frame that paints that sequence; native production-to-write is measured separately | Visible-tab receive-to-paint p95 stays within one actual display refresh interval, and camera-to-display latency is measured externally rather than inferred across unrelated clocks ([MDN high-resolution timing](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/High_precision_timing)) |
| Linux fake/nested | A recording sink verifies bounds, coalescing, state transitions, and release-on-every-exit path; libei's demo EIS server or a nested Weston session receives valid sequences ([libei API](https://libinput.pages.freedesktop.org/libei/api/index.html), [Wayland compositor types](https://wayland.freedesktop.org/docs/book/Compositors.html)) | Kill and stale-data paths succeed every time without controlling the real desktop |
| Real pointer | Startup is disarmed, movement is bounded to the selected display, loss freezes immediately, Xorg/Wayland mismatch fails clearly, and consent requests pointer only | Movement survives a supervised session before any click capability exists |

Timeout, smoothing, confidence, speed limits, and click thresholds cannot be selected from platform documentation. They must come from measured camera noise, actual display geometry, and C9 accuracy/jitter/latency data. This is also why the browser stage is valuable: it is a visible safety harness for the same normalized stream, not throwaway UI work.

## Conclusion

The browser-to-Linux progression works only if the browser is treated as the first output sink, not as the tracking system or an imitation operating system. That framing preserves one calibrated coordinate contract while progressively increasing privilege: DOM overlay, Xorg XTEST, then user-authorized Wayland EIS. It also exposes the true critical path: finish enough calibration and fusion to produce a trustworthy `valid` sample before spending effort on clicks or packaging.

The shortest complete next milestone is therefore a tested normalized sample plus a deterministic loopback SSE browser demo. It proves orientation, bounds, freshness, latency instrumentation, and disarming now, while leaving exactly one seam for the future real cursor.

*Skipped: implementation, live cursor injection, dependency installation, gesture design, and GNOME/KDE Wayland permission testing.*
*Risk: the real tracked cursor remains blocked by unfinished calibration/fusion; unsafe validity or stale-data handling would turn tracking errors into desktop input.*
